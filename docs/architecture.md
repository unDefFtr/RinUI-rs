# `rinui-rs` Architecture

## 1. Design Principles

`rinui-rs` replaces RinUI's Python/PySide6 runtime (`RinUI/core/`) with a reusable Rust + C++/Objective-C++ Qt 6 host while keeping `upstream/Rin-UI` completely unmodified as a pinned Git submodule.

Key invariants:

1. **Unmodified Upstream Submodule**: Compatibility fixes (`qmldir` sanitization, broken file exclusion, versionless singleton normalization) happen in `$OUT_DIR/rinui_sanitized/` at Cargo build time (and in per-engine/per-session temporary `ResourceView` staging directories in filesystem dev mode), never inside `upstream/Rin-UI`.
2. **Thread-Safe Main-Thread Ownership**: `RinUIRuntime<'app>`, `RinUISession<'app>`, `SessionHandle<'app>`, `EngineConfigurator<'_>`, `NativeWindowRef`, `RinUIHost`, and `HostHandle` are `!Send + !Sync`. No public API allows raw cross-thread `QObject` mutation.
3. **4-Layer Runtime / Engine / Session Ownership**:
   - **Layer 1 — Process-Level `RinUIRuntime<'app>` (backed by `Rc<RuntimeCore>`)**: Owns or borrows the process's single `QGuiApplication` (compatible with `QApplication` subclasses), holds `ConfigStore`, the `ThemeManager` QObject (guarded by `theme_borrow_state: Rc<Cell<isize>>` reader-writer tracking via `!Send + !Sync` `ThemeManagerRef<'_>` / `ThemeManagerMut<'_>` and `mut_slot_active` QML slot re-entrancy protection), global `TranslationManager`, runtime-lifetime native services (such as Windows `WinEventManager`), optional shared `EngineState`, and the live engine registry (`HashMap<u64, *mut QQmlApplicationEngine>`). Shared via `Rc<RuntimeCore>` so even if a caller drops `RinUIRuntime` before an active `RinUISession`, runtime services remain alive until the final session drops.
   - **Layer 2 — `EngineState`**: Owns a `QQmlApplicationEngine`, heap context `QObject`s (`owned_context_objects`), registered context property keys (tracking `ContextPropertyConflict::{Reject, Overwrite}`), and the prepared `ResourceView` (ordered after `engine` so the temporary filesystem view outlives the engine and QML roots). Created either as the runtime's single `Shared` engine or per-session `Private` engine.
   - **Layer 3 — `RinUISession<'app>` & `SessionHandle<'app>`**: Owns a unique `session_id`, tracks its own loaded `RootId`s and `WindowCustomizer`, selects `EngineMode::Shared` or `EngineMode::Private`, and binds its lifetime `'app` to the underlying `QGuiApplication` borrow (`'static` for owned applications). Disposing a `RinUISession` immediately marks all cloned `SessionHandle`s as disposed, releases only this session's `RootId`s/windows and private engine (always queued for deferred destruction, including callbacks driven directly by the external app), and leaves sibling sessions untouched.
   - **Layer 4 — `RinUIHost` & `HostHandle` (`= SessionHandle<'static>`)**: Convenience standalone wrapper composing one `RinUISession<'static>` over one owned `RinUIRuntime<'static>`, preserving `RinUIHost::new(HostConfig)` single-instance ergonomics (`session` declared before `runtime` so session tears down first).
4. **Borrowed Application Preservation & Process-Global Semantics**:
   - Qt Application, default `QLocale`, installed `QTranslator`s, Quick Controls style, and `ThemeManager` are process-global. `RinUIRuntime::attach_existing(&'app QGuiApplication, ...)` (plus `unsafe attach_existing_raw`) snapshots the caller's pre-existing `QLocale`, `windowIcon`, and application identity (`organizationName`, `applicationName`, `applicationDisplayName`, `applicationVersion`, `desktopFileName`), refuses late incompatible Quick Controls style changes once Quick Controls is active, refuses nested `exec()` on borrowed apps, preserves caller-owned windows/objects, and restores snapshotted settings when the last `RuntimeCore` reference drops.
   - Calling `set_language()` or `register_translation_catalog()` updates installed `QTranslator`s transactionally and invokes `QQmlEngine::retranslate()` + `QEvent::LocaleChange` delivery across **all** registered live `Shared` and `Private` engines (iterating engine ID snapshots and re-checking `live_engines` per step so translation callbacks dropping sessions never touch freed engines).
5. **Owner-Scoped C++ Registries & Monotonic IDs**:
   - C++ maintains monotonic `u64` `RootId` and `WindowId` tables tagged with `(runtime_id, engine_id, session_id)` and a live `QQmlEngine* -> engine_id` map.
   - `release_root`, `is_root_alive`, `close_secondary_windows`, `open_window_count`, `sync_windows`, `register_window_from_property`, and `set_root_property`/`get_root_property`/`invoke_root_method` enforce `session_id` ownership (`release_root` also schedules deletion for explicitly registered detached windows whose parent is null).
   - `resolve_window_owner()` attributes dynamic top-level `QQuickWindow`s via `_rinuiOwnerSessionId`, `QObject::parent` chain, `QWindow::transientParent` chain, and `QQmlContext::parentContext()->contextObject()` creation context. On `EngineMode::Shared`, `sync_windows()` never auto-claims unattributed (`session_id == 0`) windows (e.g., singleton-created detached windows); callers attribute them explicitly via `register_window_from_property(root_id, prop)` (`HostError::{WindowNotOwned, WindowRegistrationFailed}`).
6. **Deterministic Qt Destruction Order & Callback Safety**:
   - **QML and ThemeManager guards**: QML-dispatching host calls push `QmlExecGuard`; `ThemeManagerRef` / `ThemeManagerMut` enforce reader/writer borrowing, and mutating slots retain `mut_slot_active` protection. Both guards maintain per-runtime state and thread-local `GLOBAL_QML_EXEC_DEPTH` / `GLOBAL_THEME_BORROW_ACTIVE`. A caller's direct `app.process_events()` may run a QML callback with neither a Rust execution guard nor a positive Qt `loopLevel()`, so Session destruction never relies on those indicators to decide whether to delete an engine synchronously.
   - **`EngineState`**: destruction order is `engine` -> `owned_context_objects` -> `resource_view`. Cache clearing and garbage collection run only while `rinui_has_live_gui_application()` is true; ordinary engine destruction still releases resources during application post routines.
   - **`RinUISession` Drop**: invalidate handles immediately (`inner = None`), drop its customizer, and always call `rinui_session_release_all`. Remove owned roots/windows from C++ registries, mark windows `_rinuiReleased`, detach native window hooks, and use `deleteLater()` without synchronous `hide()` / `releaseResources()`. Always queue Private engines in `deferred_engine_drops`, retaining their context objects and filesystem views. Schedule a drain when execution and theme guards are clear; otherwise guard release schedules/finishes it. Sibling sessions keep their ownership and remain callable. A self-disposed `load()` still discards unregistered roots and returns `HostDisposed`.
   - **Drain coordination**: Each borrowed Private engine gets its own `EngineDropFence` QObject via `rinui_defer_engine_drop`; a shared engine gets one when its Runtime enters pending teardown. `deleteLater()` posts the fence at the releasing callback's Qt scope/loop level. Only actual Qt `DeferredDelete` delivery marks that engine ready; ordinary timer/aboutToQuit callbacks cannot authorize it. Ready engines are selected individually, so an older ready engine cannot carry a newer engine into destruction. Pending Runtime teardown waits until all retained engines are ready (or application post-routine shutdown).
   - `rinui_schedule_deferred_drain()` still coalesces wakeups with a zero-delay timer and aboutToQuit / qAddPostRoutine hooks, but borrowed normal drains **never force global DeferredDeletes**. A wakeup firing in recursive external `app.process_events()` therefore neither deletes an unqualified engine nor flushes its still-executing root. Guard counters remain an additional fence for host/theme borrows; post routines never reschedule. Standalone guard-release flushing remains unchanged.
   - **Manual Qt drivers**: Qt does not automatically dispatch every DeferredDelete when repeatedly calling `processEvents()` without `exec()`, particularly events posted outside Qt notification delivery. Such drivers must explicitly call `QCoreApplication::sendPostedEvents(nullptr, QEvent::DeferredDelete)` at their outer boundary, after callbacks have returned. Never add that forced flush inside a QML callback. Normal application destruction remains the final fallback if no further events are dispatched. Tests use a test-support binding for this standard Qt driver step; nested app-pump callbacks themselves only call the external application's process_events, without a RinUI guard.
   - **Two-phase `RuntimeCore` Drop**: immediately unregister from `LIVE_RUNTIMES` / `ACTIVE_RUNTIME_ID`, persist configuration, and clear `live_engines`. For a borrowed app with retained engines and a live GUI, detach roots/windows with `rinui_runtime_release_windows_deferred`, remove translators, disconnect color-scheme signals and restore borrowed app state. Move engines, `ThemeManager` and `RuntimeActiveGuard` into `PENDING_RUNTIME_TEARDOWNS`; the reservation remains held after the last Runtime/Session owner disappears. Final draining proceeds in this order:
     1. For ordinary cleanup, wait for every retained engine’s Qt fence. Only post-routine shutdown may force deferred deletes if the GUI is still alive.
     2. Drop qualified deferred Private engines and the shared engine; only the post routine flushes again if the GUI is alive.
     3. Release remaining windows/filters, then runtime services.
     4. Drop `ThemeManager`; only the post routine flushes again if the GUI is alive.
     5. Drop `RuntimeActiveGuard`, releasing `RUNTIME_ACTIVE`.
   - Standalone runtimes and cases without borrowed live engines retain synchronous ordered teardown, with the owned `QGuiApplication` destroyed last. Borrowed runtimes never destroy the external app. Reattachment before the external event loop drains pending teardown returns `ApplicationAlreadyInitialized`; reattach after draining, or after application shutdown completes its post routine. Abrupt process termination cannot run these cleanup hooks.
7. **Consumer Isolation**: `rinui-host` contains zero Goosy-specific business logic, rendering, or navigation. Each consumer passes its own `AppIdentity` so configuration and logs remain strictly isolated per application.

## 2. Repository Layout

| Directory / File | Purpose |
|---|---|
| `upstream/Rin-UI` | Pinned upstream RinUI Git submodule (read-only) |
| `crates/rinui-platform` | Pure Rust OS/Windows build detection, `PlatformCapabilities`, `RinConfig`, `ConfigStore`, and atomic JSON persistence (`AppJsonStore`) |
| `crates/rinui-host` | Public Rust host API (`RinUIRuntime`, `RinUISession`, `SessionHandle`, `RinUIHost`, `HostHandle`, `ThemeManager`, `TranslationManager`, `ResourceView`, `WindowCustomizer`) and build-time RinUI QRC generator |
| `native/` | C++ & Objective-C++ Qt/OS adapters (`rinui_qt_bridge`, `rinui_theme_bridge`, `rinui_mac_window.mm`, `rinui_win_bridge`, `rinui_linux_window`) |
| `qml/` | Host smoke-test, i18n, object interop, and multi-window QML fixtures (`SmokeTest.qml`, `MultiWindowDialog.qml`, `I18nTest.qml`, etc.) |
| `examples/gallery` | Standalone Rust-hosted RinUI Gallery reusing upstream `examples/` QML + custom `RustHostDemoPage` |
| `packaging/windows` | Host-owned MSIX manifest template, assets, and packaging notes |
| `cmake/` | CMake integration helpers (`RinUIHost.cmake`, `BundleHelpers.cmake`) |
| `scripts/` | Upstream submodule audit (`audit_upstream.py`) and platform deployment/MSIX scripts |
| `docs/` | Architecture, compatibility contract, consumer guide, packaging, validation, and upstream update guide |

## 3. Resource Packaging & Anti-Shadowing

RinUI's upstream QML files mix `import RinUI` with relative imports such as `import "../../themes"`, `import "../utils"`, and `Qt.resolvedUrl("../assets/fonts/FluentSystemIcons-Resizable.ttf")`.

To keep QML canonical URL deduplication intact (avoiding duplicate singletons) **and** prevent compiled QRC resources from shadowing filesystem development mode:

- Embedded RinUI resources are mounted at QRC prefix **`/rinui/RinUI`** (never `/qt/qml/RinUI`, because `qrc:/qt/qml` is always searched implicitly by Qt).
- Under `ResourceMode::Embedded`, each `EngineState` adds `qrc:/rinui` to `QQmlApplicationEngine::addImportPath` and loads `.qm` files from `:/rinui/RinUI/languages/<locale>.qm`.
- Under `ResourceMode::Filesystem(dir)`, `ResourceView::prepare()` materializes a fresh sanitized copy in a temporary directory owned by that `EngineState` (applying the shared `qmldir_sanitize` rules used by `build.rs` without editing `upstream/Rin-UI`), adds that temporary directory (`load_root`) exclusively to `addImportPath`, omits `qrc:/rinui`, and loads `.qm` files from `<load_root>/RinUI/languages/<locale>.qm`.
- Host-side `sanitize_runtime_qml` (used identically at build time and in filesystem dev staging, keeping `upstream/Rin-UI` untouched) also rewrites default `locale` bindings in `components/DateAndTime/Calendar.qml`, `components/DateAndTime/DatePicker.qml` (plus `monthModel` referencing `datePicker.locale`), and `components/Text/SpinBox.qml` to depend on `qsTr("")` while preserving explicit caller declarative/imperative `locale:` / `calendarLocale:` overrides; `rinui_engine_retranslate()` pairs `QQmlEngine::retranslate()` with deduplicated `QEvent::LocaleChange` delivery across live registered roots, items, and windows.

## 4. Platform Window Integration

- **macOS (`native/src/rinui_mac_window.mm`)**: Uses ARC Objective-C++ to configure `NSWindowTitleHidden`, `setTitlebarAppearsTransparent:YES`, `setMovableByWindowBackground:NO`, `NSWindowStyleMaskFullSizeContentView`, `NSAppearance` Light/Dark/Auto synchronization, and idempotent traffic-light container offsetting across retries, `visibleChanged` (connection tracked and disconnected per window on teardown), `Show`/`Expose` fallback retries, resize, and fullscreen exit. Pre-first-frame framing selection is injected via the QML context property `RinUINativeMacFrame`, while `setup_window()` / `apply_macos_window_style()` record `_rinuiMacFrameDiagnostic` on every registered `QQuickWindow`. Guarded on `QGuiApplication::platformName() == "cocoa"` so headless `offscreen` runs keep QML `useNativeMacFrame` intact for inspection while skipping Cocoa calls.
- **Windows (`native/include/rinui_win_bridge.h`, `native/src/rinui_win_bridge.cpp`)**: Implements `WinEventManager` (`Q_OBJECT`, held with Runtime lifetime via `std::unique_ptr` with `parent = nullptr` so multi-engine sessions never lose it when the first engine drops) and `WinEventFilter` (`QAbstractNativeEventFilter`) for `WM_NCCALCSIZE`, `WM_GETMINMAXINFO`, `WM_NCHITTEST`, Win11 Snap Layouts `HTMAXBUTTON`, DWM `DWMWA_SYSTEMBACKDROP_TYPE` / `DWMWA_MICA_EFFECT` / Win10 `SetWindowCompositionAttribute` (including `ACCENT_DISABLED` when switching back to `"none"`), and transparent render clear hooks.
- **Linux (`native/src/rinui_linux_window.cpp`)**: Uses Qt's compositor-supported `FramelessWindowHint` and `startSystemResize()`, and returns `-2` gracefully from `apply_backdrop_effect`.
